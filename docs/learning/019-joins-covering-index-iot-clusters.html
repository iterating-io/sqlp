조인 방식과 테이블 저장 구조

2장 두 번째 절 · NL·해시 조인의 선택과 커버링 인덱스, IOT, 클러스터 테이블이 블록 접근에 미치는 영향을 정리합니다. Oracle 기준이며 다른 DBMS의 문법은 구분합니다.

NL 조인: 행마다 반복하는 안쪽 탐색

NL(Nested Loops) 조인은 바깥쪽에서 행을 하나 꺼낼 때마다 안쪽에서 조인 조건에 맞는 행을 찾습니다. 중첩 반복문 형태이지만 모든 조합을 만드는 카티션 곱과 같지는 않습니다. 인덱스가 있으면 매번 안쪽 전체를 확인하는 대신 일치하는 범위를 탐색할 수 있습니다. 인덱스 사용 자체가 NL 조인의 정의는 아닙니다.

각 고객에 대해:
    주문 고객번호 인덱스에서 해당 고객의 주문 탐색
    → ROWID로 필요한 주문 행 조회
    → 고객과 주문 결합

핵심은 바깥쪽 결과 행 수가 안쪽 탐색의 반복 횟수를 결정하고, 안쪽 인덱스가 한 번의 탐색 범위를 줄여 준다는 것입니다. 테이블 접근이 필요하면 클러스터링 팩터와 캐시 재사용도 비용에 영향을 줍니다.

해시 조인: 임시 해시 테이블로 짝 찾기

일반적으로 조건을 적용한 뒤 작은 쪽 데이터로 조인 키 기반 해시 테이블을 메모리에 만듭니다(Build). 다른 쪽을 읽으면서 같은 키를 해시 테이블에서 찾아 결합합니다(Probe). 해시값이 같아도 실제 키가 같은지 확인합니다.

고객 데이터 → 고객번호별 해시 테이블 생성
주문 데이터 → 주문마다 고객번호로 해시 조회 → 고객과 결합

대량의 동등 조건(=) 조인에 유리한 경우가 많고, 해시 테이블이 메모리에 들어갈 때 효율적입니다. 메모리가 부족하면 임시 디스크 작업이 늘 수 있습니다. 입력을 읽는 경로는 전체 스캔일 수도 인덱스 탐색일 수도 있습니다.

1:1·1:N·N:M은 데이터 관계이고, NL·해시는 실행 방법입니다. 고객 1명에 주문 100건이면 어느 방식으로 조인해도 조건이 같다면 100개 조합을 반환합니다.
방법주로 유리한 상황확인할 비용
NL + 인덱스소량을 골라 조회하고 안쪽을 효율적으로 탐색반복 횟수, 탐색·테이블 블록 접근량
해시 조인많은 데이터를 동등 조건으로 결합입력 읽기량, 해시 메모리, 임시 영역 사용

서비스 조회라도 대량 처리일 수 있고, 배치라도 일부 데이터만 대상일 수 있습니다. 업무 이름보다 실제 처리량을 기준으로 판단합니다. 인덱스로 정렬을 생략하려면 조건과 인덱스 컬럼 순서가 맞아야 합니다. 파티셔닝도 프루닝으로 제외할 범위가 있어야 전체 읽기량을 줄일 수 있습니다.

조인 힌트

SELECT /*+ LEADING(c) USE_NL(o) */ c.고객명, o.주문번호
FROM 고객 c JOIN 주문 o ON o.고객번호 = c.고객번호;

SELECT /*+ USE_HASH(o) */ c.고객명, o.주문번호
FROM 고객 c JOIN 주문 o ON o.고객번호 = c.고객번호;

LEADING(c)는 조인 순서를, USE_NL(o)는 o를 안쪽으로 하는 NL 조인을, USE_HASH(o)는 o와의 해시 조인을 지정하는 힌트입니다. USE_NL만으로 인덱스 사용까지 지정되지는 않습니다. 힌트가 무시되거나 적용 불가능할 수 있으므로 실제 실행계획으로 확인합니다.

조회용 컬럼과 커버링 인덱스

쿼리에 필요한 컬럼을 모두 인덱스에 담으면 별도 테이블 접근을 생략할 수 있습니다. 이를 해당 쿼리를 커버하는 인덱스라고 합니다. Oracle의 일반 B-tree에서는 조회용 컬럼도 키 뒤쪽에 추가하므로 정렬에 참여합니다.

CREATE INDEX 주문_IX ON 주문 (고객번호, 주문일, 주문금액);

SELECT 주문일, 주문금액 FROM 주문
WHERE 고객번호 = 100 ORDER BY 주문일;

정렬 순서는 고객번호 → 주문일 → 주문금액입니다. 주문금액을 뒤에 추가해도 앞의 키 순서는 유지됩니다. SQL Server와 PostgreSQL의 INCLUDE는 조회용 컬럼을 정렬 키에서 분리해 저장하는 문법입니다. 컬럼 추가는 인덱스 크기와 변경 시 유지 비용을 늘립니다.

IOT와 오버플로

IOT(Index-Organized Table)는 기본키 B-tree의 리프에 행 데이터 자체를 저장합니다. 별도 힙 테이블에 원본을 두고 일부 컬럼을 복제하는 커버링 인덱스와 구분됩니다.

오버플로 영역을 지정하면 설정된 기준에 따라 일부 비키 컬럼을 별도 세그먼트에 저장할 수 있습니다. 리프에는 나머지 행 부분을 가리키는 포인터가 남습니다.

리프의 컬럼만 필요 → 리프에서 조회 완료
오버플로 컬럼 필요 → 리프 → 포인터 → 오버플로 블록 접근

추가 블록이 캐시에 없으면 물리적 읽기가 발생할 수 있습니다. 자주 조회하는 컬럼은 리프에, 크고 드물게 쓰는 컬럼은 오버플로에 두는 방식으로 균형을 잡습니다.

IOT 오버플로는 길이 제한 없는 타입만을 위한 기능이 아닙니다. 일반 컬럼도 대상이 됩니다. Oracle의 CLOB 같은 LOB의 별도 저장은 다른 저장 메커니즘입니다. 큰 값을 읽는 데 여러 블록이 필요할 수 있지만, 모든 접근이 랜덤 디스크 I/O인 것은 아닙니다.

클러스터 테이블: 같은 키의 행을 모아 저장

구분인덱스 클러스터해시 클러스터
공통 목적같은 클러스터 키의 행을 함께 저장해 관련 데이터의 블록 접근을 줄임
접근 방법별도 클러스터 인덱스에서 키를 찾아 블록 접근키에 해시 함수를 적용해 대상 저장 위치 계산

같은 키의 행이 반드시 한 블록에 모두 들어가는 것은 아닙니다. 많으면 추가 블록으로 이어질 수 있고, 한 블록에 여러 키가 들어갈 수도 있습니다. 해시 클러스터는 서로 다른 키가 같은 해시값을 갖는 충돌과 저장 공간 부족으로 추가 접근이 발생할 수 있습니다. 여러 테이블의 관련 행을 같은 블록에 함께 저장하는 것도 가능합니다.

파티셔닝은 테이블을 별도 저장 단위로 나누는 구조입니다. 같은 고객의 행이 같은 파티션에 있어도 그 안의 여러 블록에 흩어질 수 있습니다. 클러스터는 관련 행을 블록 수준에서 모으고 찾는 방식에 초점을 둡니다.

해시 조인은 쿼리 실행 중 결합을 위해 만드는 작업 구조이고, 해시 클러스터는 데이터를 지속적으로 저장하는 구조입니다. 같은 해시를 사용해도 역할이 다릅니다.
