부분범위처리·정렬·배치 I/O

2장 세 번째 절 · 필요한 만큼 먼저 반환하는 처리와 전체 입력이 필요한 정렬, 배치 접근이 결과 순서에 미치는 영향을 정리합니다. Oracle 기준입니다.

부분범위처리와 커서

부분범위처리는 전체 결과를 끝까지 처리하기 전에 필요한 만큼 먼저 처리해 반환하는 방식입니다. 같은 SQL 실행의 커서를 유지하면 다음 FETCH에서 실행 상태를 이어받아 처리를 계속할 수 있습니다. FETCH 단위에는 클라이언트 드라이버의 버퍼링과 미리 읽기도 영향을 주므로, 반환한 행 수와 내부에서 처리한 행 수가 정확히 같다는 뜻은 아닙니다.

SQL 실행 → FETCH로 앞의 50행 반환
        → 커서와 실행 상태 유지
        → 다음 FETCH로 이어서 처리

여기서 다음 요청은 같은 커서에 대한 FETCH 호출입니다. SQL을 새로 실행하거나 별도 웹 요청으로 페이지를 조회하면 기존 커서의 위치를 자동으로 이어받지 않습니다. 커서를 닫거나 실행 상태를 잃으면 그대로 재개할 수 없습니다.

결과를 여러 번 나누어 받는다는 사실만으로 부분범위처리는 아닙니다. 첫 결과를 반환하기 전에 전체 입력을 처리해야 하는 연산이 있는지 확인해야 합니다.

정렬이 첫 결과를 늦추는 이유

일반적인 ORDER BY 정렬은 정렬 대상 전체를 읽어야 가장 앞에 올 행을 확정할 수 있습니다. 따라서 클라이언트가 50행만 요청해도 그 전에 전체 정렬 입력을 읽는 작업이 필요합니다. 이때 전체 범위는 테이블 전체가 아니라 조회 조건을 통과해 해당 정렬에 들어오는 데이터 전체입니다.

별도 정렬 필요:
조건에 맞는 입력 전체 읽기 → 정렬 → 결과 반환

인덱스 순서로 ORDER BY 충족:
순서에 맞춰 인덱스 접근 → 필요한 만큼 먼저 반환 가능

정렬 컬럼이 인덱스에 있다는 것만으로는 정렬을 생략할 수 없습니다. 조회 조건, 인덱스 컬럼 순서와 방향, 실행계획의 다른 연산까지 원하는 순서를 충족해야 합니다. 적합한 인덱스로 ORDER BY를 충족하면 실행계획에 별도의 SORT ORDER BY가 없어도 정렬된 결과를 반환할 수 있습니다.

상위 N행 정렬은 전체 결과를 완전히 정렬하는 대신 후보를 줄여 메모리와 정렬 비용을 아낄 수 있습니다. 그래도 입력이 원하는 순서로 제공되지 않으면 보통 후보 입력 전체를 확인해야 합니다. 반환 행 수가 적다는 이유만으로 입력 읽기까지 적다고 판단하지 않습니다.

Sort Area와 TEMP

정렬은 먼저 메모리 작업 영역에서 수행합니다. 메모리 안에서 끝나면 TEMP를 사용하지 않고, 할당된 메모리로 부족하면 중간 정렬 결과를 TEMP의 임시 세그먼트에 기록하고 다시 읽으며 처리합니다.

상황정렬 작업첫 결과 전 전체 입력 확인
메모리 충분메모리에서 정렬일반적인 전체 정렬에서는 필요
메모리 부족메모리와 TEMP를 이용해 정렬필요하며 임시 영역 I/O도 추가될 수 있음

TEMP 사용 여부와 부분범위처리 가능 여부는 별개입니다. 메모리에서 정렬을 끝내도 전체 입력을 읽어야 할 수 있습니다.

배치 I/O와 ROWID 배치 접근

필요한 블록이 캐시에 없을 때마다 읽기 완료를 건건이 기다리는 비용을 줄이기 위해, 여러 블록의 읽기 요청을 모아 처리할 수 있습니다. 이것이 흩어진 모든 블록을 한 번의 연속 읽기로 가져온다는 뜻은 아닙니다.

Oracle 실행계획의 TABLE ACCESS BY INDEX ROWID BATCHED는 인덱스에서 ROWID 여러 개를 모은 뒤 블록 순서로 행에 접근하려는 방식입니다. 같은 블록의 행들을 함께 방문하면 블록을 반복해서 접근하는 횟수를 줄일 수 있습니다. 읽기 요청을 묶는 것과 ROWID 접근 순서를 재배치하는 것은 구분합니다.

인덱스에서 얻은 ROWID가 가리키는 블록:
A → C → A → B

배치 내 접근 재배치의 개념:
A → A → B → C

위 예는 블록 접근을 설명하기 위한 개념도입니다. 모든 배치가 항상 이 순서로 처리되거나, 전체 결과가 블록 순서로 정렬된다는 보장은 없습니다. 배치 단위로 처리하므로 배치 접근 자체가 전체 결과를 모아 정렬해야 한다는 뜻도 아닙니다.

인덱스 순서에 기대도 되는가?

인덱스 리프를 키 순서로 읽고 각 ROWID를 즉시 따라가면 결과도 키 순서처럼 보일 수 있습니다. 그 순서에 익숙한 애플리케이션에서는 배치 접근 도입이나 실행계획 변경으로 순서가 달라질 때 혼선이 생길 수 있습니다.

그러나 SQL 결과의 순서가 업무상 필요하면 최종 ORDER BY로 명시해야 합니다. 인덱스의 물리적인 탐색 순서는 실행 방법의 속성이고, ORDER BY는 쿼리가 요구하는 결과 순서입니다. 옵티마이저는 명시된 순서를 지키는 범위에서 실행 방법을 선택해야 합니다.

SELECT 주문번호, 주문일
FROM 주문
WHERE 고객번호 = :고객번호
ORDER BY 주문일, 주문번호;

같은 주문일의 행들 사이에서도 안정적인 순서가 필요하다면 주문번호처럼 순서를 구별할 수 있는 키를 함께 지정합니다. ORDER BY가 있어도 적합한 인덱스를 사용하면 별도 정렬 없이 반환할 수 있습니다.

배치 접근을 제어하는 NO_BATCH_TABLE_ACCESS_BY_ROWID 힌트도 있습니다. 이는 특정 접근 방식을 억제하기 위한 수단입니다. 배치 접근을 막았다는 사실만으로 ORDER BY 없는 결과의 순서가 보장되지는 않습니다. 적용 여부와 성능 효과는 사용 중인 버전의 실제 실행계획으로 확인합니다.

블록 접근 순서를 바꾸는 배치 최적화와 결과를 원하는 순서로 반환하는 ORDER BY는 서로 다른 역할입니다. 정렬 보장은 ORDER BY에 맡기고, 인덱스와 배치 접근은 그 요구를 만족시키는 실행 비용 관점에서 판단합니다.
