Oracle USE_CONCAT과 MySQL Index Merge

OR 확장과 여러 인덱스 결과 결합을 구분하고 MySQL에서 대응할 수 있는 힌트를 살펴봅니다.

Oracle USE_CONCAT은 쿼리 변환 힌트

USE_CONCAT은 인덱스 스캔 자체를 지정하는 힌트라기보다, WHERE의 OR 조건을 UNION ALL 분기로 바꾸는 OR 확장 힌트입니다. 분기마다 옵티마이저가 접근 경로를 따로 검토할 수 있어 인덱스 사용에 도움이 될 수 있지만, 이 힌트가 특정 인덱스 스캔을 지정하는 것은 아닙니다.

SELECT /*+ USE_CONCAT */ *
FROM t
WHERE a = 10 OR b = 20;

MySQL의 가까운 기능은 Index Merge

MySQL 8.4에는 Oracle의 OR 확장처럼 쿼리를 UNION ALL 분기로 바꾸라고 지시하는 대응 힌트가 없습니다. 대신 한 테이블에서 여러 인덱스를 range scan하고 그 결과를 합치는 Index Merge 접근 방식이 있습니다. OR 조건과 인덱스가 맞으면 union 또는 sort_union 알고리즘이 후보가 됩니다.

SELECT /*+ INDEX_MERGE(t idx_a, idx_b) */ *
FROM t
WHERE a = 10 OR b = 20;

INDEX_MERGE는 지정한 인덱스를 이용한 Index Merge를 유도하고, NO_INDEX_MERGE는 이를 막습니다. 인덱스 조합이 해당 문장에 적용될 수 없으면 힌트가 무시될 수 있습니다. 이 기능은 OR 조건을 별도의 SQL 분기들로 바꾸는 대신, 한 테이블에서 나온 인덱스 스캔의 행 ID를 결합합니다.

실행 계획의 type이 index_merge인지, Extra에 Using union(...) 또는 Using sort_union(...)가 나오는지 EXPLAIN으로 확인할 수 있습니다.

분기별 접근 경로를 원한다면

쿼리를 직접 UNION ALL로 나누면 각 분기의 조건과 접근 경로를 별도로 계획할 수 있습니다. 다만 한 행이 두 OR 조건을 모두 만족할 때 결과에 중복으로 나타나지 않도록 분기를 서로 배타적으로 만들거나 중복 제거를 설계해야 합니다.

요약: MySQL의 INDEX_MERGE는 OR 검색에서 여러 인덱스의 행 ID를 합치는 접근 경로입니다. Oracle USE_CONCAT처럼 OR 조건을 UNION ALL 쿼리 블록으로 확장하는 힌트와는 역할이 다릅니다.
