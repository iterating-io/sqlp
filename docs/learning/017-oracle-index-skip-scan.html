Index Skip Scan과 비용 판단

복합 인덱스의 선두 컬럼 조건이 빠졌을 때, 후행 컬럼 조건으로 탐색하는 원리와 옵티마이저의 선택 기준을 정리합니다.

핵심: 선두 값마다 후행 컬럼 범위를 탐색

복합 인덱스 (gender, email)에서 엔트리는 먼저 gender, 그 안에서 email 순서로 정렬됩니다. 쿼리가 WHERE email = :email만 지정하면, 전체 인덱스에서 이 이메일 하나가 차지하는 단일 연속 구간을 바로 알 수 없습니다. 이메일 값들이 gender별 구간에 나뉘어 있기 때문입니다.

선두 컬럼의 값이 적다면 Oracle은 값을 하나씩 가정해 하위 인덱스처럼 탐색할 수 있습니다. 예를 들어 gender가 F, M 두 값이면 개념적으로 다음 두 범위를 확인합니다.

(gender = 'F' AND email = :email)
(gender = 'M' AND email = :email)

각 선두 값에 해당하는 논리적 하위 인덱스에서 email 범위를 찾고, 조건에 맞지 않는 인덱스 블록은 건너뜁니다. Oracle 문서는 이를 개념적으로 여러 탐색의 UNION ALL처럼 설명하지만, 실제 SQL을 여러 문장으로 바꾸어 실행한다는 뜻은 아닙니다.

Skip Scan은 인덱스 전체를 무조건 읽는 Full Scan이 아닙니다. 선두 컬럼 값별로 후행 컬럼의 일치 범위를 찾아 읽는 접근 경로입니다.

언제 유리한가

  • 쿼리 조건에 인덱스의 선두 컬럼이 빠져 있습니다.
  • 선두 컬럼의 서로 다른 값이 적어 반복 탐색 횟수가 적습니다.
  • 조건에 사용된 후행 컬럼은 값의 종류가 많고, 조건이 적은 행만 선택합니다.
  • 찾은 행의 ROWID로 테이블을 방문하는 비용까지 포함해도 다른 접근 경로보다 쌉니다.

예를 들어 (gender, email) 인덱스에서 성별 값은 두 종류뿐이고 이메일은 대부분 고유하다면, 이메일 하나를 찾기 위해 두 하위 범위만 탐색하는 방법이 전체 인덱스나 테이블을 읽는 것보다 쌀 수 있습니다. 필요한 결과 컬럼이 인덱스에 없으면 실행 계획에는 보통 TABLE ACCESS BY INDEX ROWID도 나타납니다.

왜 항상 Skip Scan을 선택하지 않을까?

선두 컬럼의 값이 많으면 값마다 인덱스 탐색을 반복해야 합니다. 후행 컬럼 조건이 많은 행을 반환하면 ROWID를 따라 테이블 블록을 많이 방문하게 됩니다. 이때는 인덱스 전체 스캔이나 테이블 전체 스캔이 더 저렴할 수 있습니다. 작은 테이블은 조건이 꽤 선택적이어도 전체 스캔이 더 쌀 수 있습니다.

옵티마이저는 Skip Scan만 보는 것이 아니라 사용 가능한 접근 경로들의 예상 비용을 비교합니다. 선두 컬럼의 서로 다른 값 수, 후행 조건의 선택도와 예상 행 수, 인덱스 크기, 테이블 블록 수, ROWID 테이블 접근량, 통계의 정확도 등이 판단에 영향을 줍니다. 따라서 “선두 컬럼 값이 적다”는 것은 중요한 유리 조건이지, Skip Scan을 반드시 실행해야 한다는 규칙은 아닙니다.

상황예상 판단
선두 컬럼 값이 적고 후행 조건이 매우 선택적반복하는 하위 범위 탐색이 적어서 Skip Scan이 유리할 수 있음
선두 컬럼 값이 많음반복 탐색 비용이 커져 Skip Scan의 이점이 줄어듦
후행 조건이 많은 행을 반환ROWID 테이블 접근이 늘어 Table Full Scan이 더 유리할 수 있음
테이블이 작거나 다른 인덱스가 더 선택적전체 스캔 또는 다른 인덱스 경로가 더 쌀 수 있음
 
SELECT *
FROM customers
WHERE email = :email;

TABLE ACCESS BY INDEX ROWID
  INDEX SKIP SCAN  CUSTOMERS_GENDER_EMAIL_IX

실행 계획의 INDEX SKIP SCAN 여부와 그 위의 테이블 접근 단계, 예상 행 수와 비용을 함께 확인합니다. Skip Scan이 자주 유리한 쿼리라면 후행 컬럼을 선두로 둔 별도 인덱스가 더 직접적인 접근 경로인지도 검토할 수 있습니다.
