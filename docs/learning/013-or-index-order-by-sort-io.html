OR·IN 조건과 ORDER BY 정렬 I/O

인덱스 접근 결과와 정렬 순서, 메모리·임시 디스크 I/O를 구분합니다.

OR와 IN이 항상 비효율적인 것은 아니다

A OR B라고 해서 언제나 인덱스가 비효율적인 것은 아닙니다. 옵티마이저는 조건의 선택도와 예상 비용에 따라 여러 인덱스의 결과를 합치거나 OR 확장을 검토하고, 조건에 맞는 행이 많으면 테이블 스캔을 고를 수도 있습니다.

같은 컬럼의 여러 값은 별개의 인덱스를 합치는 경우와 다릅니다. 예를 들어 status IN ('A', 'B', 'C')는 해당 인덱스에서 여러 동등 범위로 처리될 수 있습니다. 이는 status = 'A' OR status = 'B' OR status = 'C'와 같은 값 조건을 나타내지만, 실행 방식과 정렬 결과는 실행 계획에 따라 확인해야 합니다.

MySQL의 Index Merge에서 sort_union이 행 ID를 정렬하더라도, 그 정렬은 ORDER BY가 요청한 컬럼 순서를 보장하지 않습니다.

인덱스 순서를 이용할 수 있는 경우

결과 순서는 ORDER BY가 지정할 때만 보장됩니다. 옵티마이저가 선택한 인덱스 접근이 정렬 컬럼과 순서에 맞으면 그 인덱스 순서대로 읽어 별도 정렬을 생략할 수 있습니다. 인덱스가 존재한다는 사실만으로 정렬이 생략되지는 않습니다. OR 조건을 처리하기 위해 다른 인덱스들을 결합하면 그 결과가 별도의 ORDER BY 순서에 맞는다는 보장도 없습니다.

SELECT id, title
FROM article
WHERE status = 'OPEN' OR owner_id = 10
ORDER BY created_at DESC;

status와 owner_id 인덱스가 후보 행을 찾더라도, created_at 순서를 제공하지 않으면 별도 정렬이 필요할 수 있습니다. created_at 인덱스를 읽으며 조건을 검사하는 계획도 가능하지만, 조건에 맞지 않는 행을 많이 읽게 되면 옵티마이저가 다른 접근과 정렬을 선택할 수 있습니다.

별도 정렬은 메모리에서 끝날 수도 있다

선택한 접근 인덱스에 정렬 컬럼이 없으면 옵티마이저는 정렬 키를 얻기 위해 테이블 행을 읽고 별도 정렬 단계를 수행할 수 있습니다. 그렇다고 정렬 자체가 곧 디스크 I/O를 뜻하지는 않습니다. 정렬 작업 공간에 들어가면 메모리에서 끝나며, 입력이 커서 메모리에 들어가지 않으면 임시 공간에 정렬 결과를 기록하고 다시 읽는 I/O가 생깁니다.

또한 인덱스에 정렬 컬럼이 없어서 테이블 행을 찾아야 하는 비용과, 정렬이 메모리를 넘겨 임시 공간을 쓰는 비용은 별개입니다. 테이블 블록이 버퍼 캐시에 있으면 디스크에서 다시 읽지 않을 수 있고, 캐시에 없으면 행 조회에서 물리적 읽기가 발생할 수 있습니다.

  • MySQL: EXPLAIN의 Using filesort는 별도 정렬이 있다는 뜻이지, 정렬 데이터가 반드시 디스크 파일에 기록됐다는 뜻은 아닙니다. 정렬 버퍼를 넘는 경우 임시 디스크 파일을 사용할 수 있습니다.
  • Oracle: 정렬 작업은 PGA의 work area에서 수행됩니다. 입력이 작업 공간에 들어가지 않으면 one-pass 또는 multi-pass로 처리하며 임시 공간 I/O가 추가될 수 있습니다.
따라서 “인덱스에 없는 컬럼으로 정렬하면 디스크 I/O가 증가한다”는 말은 조건부입니다. 테이블 블록을 읽는 I/O는 발생할 수 있지만, 정렬 단계의 디스크 I/O는 결과량과 메모리 작업 공간에 달려 있습니다.

실행 계획에서 볼 것

MySQL은 EXPLAIN에서 Using filesort가 있는지 확인하고, 실제 임시 파일 사용 여부는 optimizer trace의 number_of_tmp_files와 메모리 사용량으로 구분할 수 있습니다. Oracle은 실행 계획의 SORT ORDER BY와 실제 work area 통계를 함께 봅니다. 어느 쪽이든 실행 계획만으로 물리 디스크 읽기가 있었는지 단정하지 말고, 실제 실행 통계와 캐시 상태를 같이 확인해야 합니다.
