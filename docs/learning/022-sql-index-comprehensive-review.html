SQL 처리와 Oracle 인덱스 종합 복습

001–021의 개념을 SQL 실행부터 저장 구조, 접근 경로와 응답 방식까지 연결합니다. Oracle B-tree 중심이며 MySQL의 Index Merge는 별도로 구분합니다. 각 절의 원문 링크에서 세부 설명으로 돌아갈 수 있습니다.

전체 흐름: SQL에서 결과 행까지

SQL은 파싱과 최적화 과정을 거쳐 실행계획으로 구체화됩니다. 옵티마이저는 조건, 통계, 인덱스와 비용을 바탕으로 접근 경로와 조인 순서를 고릅니다. 실행기는 인덱스 또는 테이블 블록을 읽고 조건을 적용해 결과를 만듭니다. 따라서 튜닝은 “인덱스를 썼는가” 하나가 아니라 예상과 실제 행 수, 읽은 블록 수, 첫 행 지연과 전체 완료 시간을 함께 살피는 일입니다.

Oracle 저장공간은 세그먼트–익스텐트–데이터 블록으로 이어지는 논리 구조를 데이터 파일에 담습니다. 테이블과 인덱스는 각자 세그먼트를 가지며, 블록은 I/O의 주요 단위입니다. 블록을 버퍼 캐시에서 찾는 논리적 읽기도 작업 비용이고, 캐시에 없어 저장장치에서 가져오는 물리적 읽기는 추가 지연을 만듭니다. 캐시 적중률이나 BCHR 하나만으로 SQL 효율을 판정할 수 없고, 불필요한 블록 방문 자체를 줄이는 것이 우선입니다. SQL 처리 원문 · 저장 구조 · I/O 튜닝 · 저장·I/O 요약

인덱스는 정렬된 탐색 구조이자 테이블 접근의 중간 단계

B-tree 인덱스는 루트와 브랜치 블록을 따라 시작 리프 블록을 찾는 수직 탐색 뒤, 필요한 리프 엔트리를 이어 읽는 수평 탐색을 합니다. 엔트리는 키 값과 ROWID 등을 담고, ROWID는 테이블 행이 있는 위치를 찾는 단서입니다. 인덱스 블록과 테이블 데이터 블록은 별개이며, 일반 인덱스 조회는 인덱스 탐색 후 ROWID로 테이블에 갈 수 있습니다. B+ 트리와 Oracle의 B* 트리는 용어를 함부로 동일시하지 말고 구현 문맥에 맞춰 읽습니다.

테이블 레코드와 인덱스 엔트리는 다른 저장 항목입니다. 인덱스가 작고 선택도가 좋으면 후보 행을 빨리 찾지만, 후보마다 테이블 블록을 랜덤하게 방문하면 전체 스캔보다 비쌀 수도 있습니다. 인덱스 리프 순서와 테이블 행 배치가 얼마나 어긋나는지 나타내는 클러스터링 팩터(CF)는 그 테이블 접근 비용을 가늠하는 단서입니다. 탐색 · 블록·ROWID·트리 · 블록과 엔트리 · 행과 엔트리 · 저장 계층 · 랜덤 I/O와 CF

복합 인덱스에서 조건은 탐색 구간을 결정한다

(A,B) 인덱스는 A 순서 안에서 B 순으로 정렬됩니다. WHERE 절에 조건을 쓰는 순서는 보통 탐색 순서를 정하지 않지만, 인덱스 키의 선두 컬럼과 조건 형태는 시작·종료 범위를 좌우합니다. A가 동등 조건이면 B 조건으로 구간을 좁히기 쉽고, A가 넓은 범위이면 B 값들이 여러 A 값 아래 흩어져 범위 안에서 필터링될 수 있습니다. 그래서 컬럼 순서는 자주 쓰는 조건 조합, 선택도, 범위 조건, 정렬·그룹 요구를 함께 보고 정합니다.

BETWEEN은 한 연속 범위를 읽고, IN은 값마다 여러 탐색을 할 수 있습니다. 값 집합이 정말 같다는 전제에서 IN이 수직 탐색을 늘리는 대신 읽는 리프 범위를 줄일 수 있습니다. IN 값이 많으면 반복 탐색 비용이 커지므로 항상 우월하지 않습니다. Skip Scan은 선두 컬럼 조건이 빠졌을 때 선두 값별로 후행 키 구간을 탐색하는 대안이며, 선두 값의 종류가 적고 후행 조건이 충분히 유리할 때 고려됩니다.

카디널리티는 실행계획 연산이 반환할 것으로 예상하는 행 수와, 컬럼의 서로 다른 값 수(NDV)를 가리키는 용례를 구분해야 합니다. NULL이 없는 10,000행에 NDV가 100이면 값당 평균은 100행이지만 실제 분포가 균등하다는 보장은 없습니다. 통계와 데이터 편향이 비용 판단에 영향을 줍니다. 튜닝·컬럼 순서 · 선두 컬럼 · BETWEEN·IN·카디널리티·Skip Scan · Skip Scan 비용

OR, 정렬, MIN/MAX: 접근 경로가 결과 요구와 만나는 지점

OR 조건은 여러 인덱스 경로를 결합하거나 조건을 분기하는 계획으로 풀릴 수 있습니다. Oracle의 USE_CONCAT은 OR 분기를 UNION ALL 형태로 변환하도록 유도하는 힌트이고, MySQL Index Merge는 여러 인덱스 결과를 결합하는 별도 기능입니다. 이름이나 목적이 비슷해도 동작이 같은 기능은 아닙니다. 결과 중복과 분기별 비용을 확인해야 합니다. 선택 조건 OR, OR-Expansion, LIKE/BETWEEN 범위와 복합 인덱스 필터는 옵션 조건과 인덱스 범위 보충 노트를 참고합니다.

인덱스 키 순서가 ORDER BY와 맞으면 별도 정렬을 피할 수 있지만, 접근 경로와 방향, 선행 키 조건이 맞아야 합니다. 결과 순서는 오직 ORDER BY가 보장합니다. 인덱스 스캔이 우연히 원하는 순서로 반환하더라도 계약으로 삼을 수 없습니다. MIN/MAX는 가장자리 키를 이용해 빠르게 찾을 수 있는 조건이 있지만 NULL, 복합 키, 필터와 계획에 따라 달라집니다. FIRST_ROWS는 첫 결과를 빨리 내는 비용 최적화 목표이지 결과 행 수 제한이나 자동 조기 종료를 뜻하지 않습니다. OR 변환과 Index Merge · OR·IN·ORDER BY · 역방향 스캔·MIN/MAX·FIRST_ROWS

스캔 유형은 “얼마나 읽고 어떤 순서를 얻나”로 비교한다

경로읽는 방식과 고려점
Index Range Scan조건에 맞는 키 구간을 읽고 ROWID로 테이블에 갈 수 있음. 선택도와 테이블 블록 접근량이 중요.
Index Full Scan인덱스 리프를 키 순서로 읽음. 정렬 요구를 만족할 수 있지만 리프 전체를 읽는 비용 고려.
Index Fast Full Scan인덱스 블록을 다중 블록 I/O로 읽는 전체 스캔. 키 순서는 보장하지 않으며 인덱스만으로 필요한 열을 제공할 때 유리할 수 있음.
Index Skip Scan선두 키의 각 값 구간을 반복 탐색. 선두 NDV와 후행 조건 선택도에 민감.
Table Full Scan테이블 블록을 대량·연속적으로 읽음. 많은 행이 필요할 때 인덱스의 반복 랜덤 접근보다 저렴할 수 있음.

“인덱스 사용”은 곧 “빠름”이 아니며, 인덱스 전체를 읽는 것이 테이블 전체보다 작고 필요한 열을 모두 포함하는지, 정렬이 필요한지, 접근이 랜덤인지 등을 비교합니다. Index Full vs Table Full · Fast Full Scan

조인과 반환 방식: 총비용과 첫 행 시간은 다르다

Nested Loops, Hash Join, Sort Merge Join은 입력 크기와 정렬·메모리 상황에 따라 선택됩니다. NL 조인은 바깥 행마다 안쪽 입력을 찾는 구조라 인덱스를 이용할 수 있지만 NL 자체가 인덱스를 뜻하지 않습니다. 작은 바깥 입력과 빠른 안쪽 탐색이 맞으면 유리하고, 반복 횟수가 많으면 부담이 됩니다. Hash Join은 대량 입력을 해시로 연결할 때 유리할 수 있습니다.

커버링 인덱스는 쿼리에 필요한 열을 인덱스가 모두 제공해 테이블 방문을 줄이는 개념입니다. IOT는 테이블 행 자체가 기본 키 순서의 인덱스 구조에 저장되는 Oracle 구조이며, 클러스터는 관련 행을 함께 저장해 특정 접근을 줄일 수 있습니다. 이들은 일반 보조 인덱스와 저장 방식이 다르며 쓰기·공간·다른 조회 패턴 비용도 함께 고려해야 합니다.

부분범위처리는 결과를 나눠 가져와 첫 화면을 빨리 보여줄 수 있습니다. 그러나 클라이언트가 fetch를 여러 번 호출했다는 사실만으로 실행이 조기 종료됐다고 단정할 수 없습니다. 정렬은 보통 전체 후보를 살펴야 첫 결과를 확정하며, 메모리가 부족하면 TEMP를 사용할 수 있습니다. 배치 I/O는 ROWID 접근을 모아 효율을 높일 수 있지만 인덱스 순서 그대로 결과가 나온다는 보장은 없습니다. 조인·저장 구조 · 부분범위·정렬·배치 I/O

실행계획을 읽을 때의 점검 순서

  1. 최종 결과와 필터·조인 조건을 확인하고 예상 행 수와 실제 행 수 차이를 본다.
  2. 각 연산이 시작하는 위치, 읽는 범위, 반복 횟수를 파악한다.
  3. 논리 읽기와 물리 읽기, 테이블 ROWID 방문, 정렬·TEMP 작업을 확인한다.
  4. 첫 행 응답과 전체 완료 중 어느 목표가 중요한지 구분한다.
  5. 인덱스만 추가하지 말고 SQL 의미, 통계, 데이터 분포, 저장 배치까지 함께 검토한다.
한 줄 요약: 실행계획은 데이터가 흐르는 방식의 설명서다. 좋은 계획은 접근 경로 이름이 아니라 필요한 결과를 적은 블록과 적절한 응답 특성으로 제공한다.

복습 질문과 답

  1. 논리 읽기는 물리 I/O인가? 아니다. 버퍼 캐시의 블록을 읽는 논리적 요청이며, 캐시 미스가 나면 물리 읽기가 동반될 수 있다.
  2. 복합 인덱스의 WHERE 조건 순서가 컬럼 순서와 같아야 하나? SQL에 적은 순서는 상관없지만 실제 키 선두와 조건 유형이 탐색 구간에 영향을 준다.
  3. 인덱스를 탔는데 느릴 수 있나? 가능하다. 많은 후보와 랜덤 테이블 블록 접근이 전체 스캔보다 비쌀 수 있다.
  4. Index Fast Full Scan 결과는 키 순서인가? 보장되지 않는다. 순서가 필요하면 ORDER BY를 써야 한다.
  5. FIRST_ROWS는 몇 행만 반환하라는 뜻인가? 아니다. 첫 행 응답을 중시하는 최적화 목표다. 행 제한은 별도로 표현해야 한다.
  6. NL 조인은 항상 인덱스를 쓰나? 아니다. 조인 알고리즘과 접근 경로는 서로 다른 선택이다.
  7. 컬럼 NDV가 100이면 각 값마다 행이 정확히 같은 수인가? 아니다. 평균 추정에 쓸 수 있지만 편향과 NULL, 통계 품질을 봐야 한다.
  8. IN이 BETWEEN보다 항상 빠른가? 아니다. 동일한 값 집합인지 확인하고 반복 탐색과 스캔량을 비교한다.
