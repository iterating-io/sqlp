인덱스 튜닝과 컬럼 순서

인덱스 스캔 비용, ROWID를 이용한 테이블 접근, 복합 인덱스의 선두 컬럼을 구분합니다.

인덱스 튜닝에서 볼 두 비용

인덱스 튜닝을 이해할 때 두 단계로 나누어 보는 것은 유용합니다.

  1. 인덱스 블록 탐색과 스캔: 루트부터 시작 리프를 찾고, 조건에 맞는 키 범위를 얼마나 읽는지 봅니다.
  2. 테이블 행 접근: 인덱스 리프에서 얻은 ROWID로 테이블 블록을 읽습니다. 쿼리에 필요한 컬럼이 모두 인덱스 안에 있으면 테이블 접근을 생략할 수도 있습니다.

따라서 인덱스 스캔 자체가 짧아도, 결과가 많은 행을 가리키고 그 행들이 여러 테이블 블록에 흩어져 있으면 테이블 접근 비용이 클 수 있습니다. 인덱스의 클러스터링 팩터는 키 순서와 테이블 행의 물리적 배치가 얼마나 가까운지 나타내며, 옵티마이저가 인덱스와 전체 테이블 스캔의 비용을 비교할 때 참고합니다.

SQL 튜닝의 목표는 랜덤 I/O만 줄이는 것일까?

불필요한 테이블 블록 접근, 특히 흩어진 ROWID를 따라가는 물리적 단일 블록 읽기를 줄이는 것은 중요한 튜닝 방향입니다. 하지만 SQL 튜닝 전체를 “랜덤 디스크 I/O 줄이기”로 한정할 수는 없습니다. 튜닝 목표는 보통 응답 시간을 줄이거나 처리량을 높이고, SQL이 쓰는 데이터베이스 자원을 더 효율적으로 활용하는 것입니다.

선택도가 낮아 많은 행을 읽어야 한다면, 인덱스를 따라 여러 블록을 따로 읽는 것보다 테이블 전체를 순차적으로 읽는 다중 블록 I/O가 더 저렴할 수 있습니다. 또한 필요한 인덱스 블록이나 테이블 블록이 버퍼 캐시에 있으면 디스크 I/O가 발생하지 않습니다. 그러므로 실행 계획과 실제 병목을 보고 접근 경로를 판단해야 합니다.

수평 탐색은 범위 안의 인덱스 엔트리를 모두 읽기 위한 과정입니다. 엔트리에서 얻은 ROWID로 테이블 행을 찾는 단계는 별도이며, 인덱스만으로 쿼리 결과를 만들 수 있으면 생략될 수 있습니다.

SQL 조건의 나열 순서와 인덱스 컬럼 순서

여기서 “순서”는 두 가지를 구분해야 합니다.

WHERE customer_id = :c AND order_date >= :d
WHERE order_date >= :d AND customer_id = :c

인덱스 (customer_id, order_date)
인덱스 (order_date, customer_id)

WHERE 절에서 AND 조건을 적은 순서를 말한다면, 두 표현은 논리적으로 같은 조건이므로 보통 인덱스 성능 차이를 만들지 않습니다. 옵티마이저가 실행 계획을 선택하며, SQL 텍스트에 적힌 조건 나열 순서가 인덱스의 컬럼 순서를 바꾸지는 않습니다.

복합 인덱스를 정의한 컬럼 순서를 말한다면 결과는 달라질 수 있습니다. (customer_id, order_date)는 customer_id만 사용하는 검색이나 두 조건을 함께 쓰는 검색에 선두 범위를 제공합니다. 반면 (order_date, customer_id)는 order_date가 선두입니다. 모든 컬럼을 동등 조건으로 조회하면 두 인덱스 모두 후보가 될 수 있지만, 성능이 항상 같다고 보장되지는 않습니다. 다른 쿼리, 범위 조건, 정렬, 키 분포에 따라 유리한 순서가 달라집니다.

선두 컬럼을 조건에 쓰지 않는 경우 일반적인 인덱스 범위 스캔은 불리하거나 사용할 수 없을 수 있습니다. Oracle은 선두 컬럼의 값 종류가 적은 경우 인덱스 스킵 스캔을 고려할 수 있지만, 이는 예외적인 접근 경로이며 선두 컬럼을 사용하는 것과 같은 성능을 보장하지 않습니다.
