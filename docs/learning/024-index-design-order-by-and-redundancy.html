인덱스 설계: 정렬·조인·중복 점검

조건의 선택도와 범위, ORDER BY, NL 조인, 중복 인덱스를 함께 고려해 인덱스의 이득과 유지 비용을 판단합니다.

보편적인 순서 공식보다 실제 조회 패턴

인덱스 설계에는 모든 쿼리에 통하는 단일한 컬럼 순서가 없습니다. 자주 실행되는 쿼리, 조건의 선택도, 정렬 요구, 테이블 방문량, 데이터 분포와 함께 인덱스의 저장 공간 및 INSERT·UPDATE·DELETE 유지 비용을 고려합니다.

예를 들어 여러 조회 패턴을 지원하는 날짜 선두 인덱스의 범위 스캔이 허용 가능한 수준일 수 있습니다. 그러나 가장 빈번한 패턴이 입력자 = :id AND 데이터생성일시 BETWEEN ...라면, 그 패턴을 위해 (입력자, 데이터생성일시) 인덱스를 추가할 수 있습니다. 나머지 패턴의 비용을 감수하면서 가장 많이 쓰는 조회를 최적화하는 업무 기반 선택입니다.

“정답이 없다”는 말은 아무 순서나 가능하다는 뜻이 아닙니다. 빈번한 쿼리와 실제 실행 비용을 근거로 선택하고, 측정 결과에 따라 인덱스를 조정한다는 뜻입니다.

동등 조건과 복합 인덱스 선두

WHERE 절에서 조건을 적는 순서는 실행 경로를 결정하지 않습니다. 인덱스의 선두 키 순서와 조건 형태가 탐색 범위를 결정합니다.

-- 인덱스: (A, B, C)
WHERE A = 10 AND B = 20 AND C BETWEEN 5 AND 9

선두의 A와 B가 동등 조건이면 그 조합으로 좁힌 뒤 C의 범위를 탐색할 수 있습니다. 동등 조건이 여러 개이고 모두 인덱스의 끊김 없는 선두 구간을 제약한다면, 이 쿼리에서 WHERE 조건의 나열 순서는 상관없습니다. 하지만 다른 쿼리가 일부 컬럼만 사용하는 경우에는 인덱스 선두 컬럼이 달라지므로 전체 설계에서 순서가 중요합니다.

-- B가 빠짐: C는 보통 탐색 시작·종료 키가 아니라 필터
WHERE A = 10 AND C BETWEEN 5 AND 9

중간의 B가 빠지면 C 값이 B 값별로 흩어질 수 있습니다. 일반적으로 A 구간을 읽으며 C 조건으로 인덱스 항목을 걸러내고, 인덱스 스킵 스캔은 비용이 유리할 때의 예외적인 대안입니다.

동등 연산자라고 무조건 선택도가 높은 것도 아닙니다. 전체 행 중 70%가 상태 = '활성'이라면 이 조건은 적은 행만 골라내지 않습니다. 선택도 비율은 조건 일치 행 수를 전체 행 수로 나눈 값이며, 비율이 낮을수록 더 많이 걸러냅니다.

ORDER BY를 피하는 인덱스와 범위 탐색의 교환

다음 쿼리에서 A가 동등 조건이고 B가 범위 조건이라고 가정합니다.

WHERE A = :a
  AND B BETWEEN :lo AND :hi
ORDER BY C
인덱스장점비용·제약
(A, B, C)A와 B로 후보 범위를 좁히기 좋음B 값별로 C 순서가 묶이므로 C 전체 정렬이 필요할 수 있음
(A, C, B)A가 고정된 범위 안에서 C 순서로 읽어 정렬을 피할 수 있음B로 스캔 범위를 좁히기 어려워 A 구간을 더 많이 읽고 B를 필터링할 수 있음

정렬을 없애는 이득과 더 많은 인덱스 항목을 읽는 비용을 비교해야 합니다. B가 동등 조건이라면 (A, B, C)에서도 A와 B가 고정되므로 C 순서를 얻을 수 있습니다. 또한 ORDER BY 앞의 인덱스 키가 고정되어야 그 뒤 키의 정렬 순서를 전체 결과에 적용할 수 있습니다. A가 여러 값의 범위라면 (A, C, ...)는 일반적으로 C만의 전역 정렬을 보장하지 않습니다.

정렬 작업의 비용

  • 후보 행을 비교하고 재배치하는 CPU 작업이 행 수에 따라 증가합니다.
  • 정렬 키와 행 위치 정보를 메모리 작업 공간에 보관합니다.
  • 작업 공간을 넘으면 TEMP에 중간 결과를 쓰고 병합하여 추가 I/O와 지연이 생길 수 있습니다.
  • 전체 정렬이 필요한 계획은 정렬할 입력을 처리하기 전 첫 행 반환이 늦어질 수 있습니다.

ORDER BY C FETCH FIRST 20 ROWS ONLY는 C 순서상 앞선 20행을 뜻합니다. 정렬된 인덱스가 있으면 조건에 맞는 20행을 찾고 멈출 수 있습니다. 인덱스가 없으면 Top-N 정렬로 상위 20행만 메모리에 유지할 수 있지만, 보통 모든 후보를 살펴야 합니다. ORDER BY가 없으면 “상위”의 순서는 정의되지 않습니다.

NL 조인에서 어느 테이블에 인덱스를 둘까?

Nested Loops 조인은 바깥 테이블의 각 행에 대해 안쪽 테이블을 반복 탐색합니다. 바깥 결과가 적고 안쪽 탐색이 빠르면 효율적이며, 안쪽 테이블의 조인 키와 추가 필터 조건에 맞는 인덱스가 반복 비용을 줄이는 경우가 많습니다.

따라서 보통은 inner 테이블의 조인 키 인덱스를 우선 검토합니다. 다만 바깥 테이블에서 후보 행을 크게 줄이는 인덱스가 더 중요할 수 있고, inner 테이블이 작거나 조인 방식이 달라지면 판단도 달라집니다. NL 조인 자체가 인덱스 사용을 보장하지는 않습니다.

중복 인덱스 실습: 같은 컬럼도 순서가 다르면 역할이 다르다

이름인덱스 키주요 접근 의미
PK(거래일자, 관리지점번호, 일련번호)거래일자 선두 범위와 기본키 보장
N1(계좌번호, 거래일자)계좌번호 동등 조건 후 거래일자 범위
N2(결제일자, 관리지점번호)결제일자 범위 중심 조회
N3(거래일자, 종목코드)거래일자 범위와 종목코드 인덱스 필터
N4(거래일자, 계좌번호)거래일자 범위 뒤 계좌번호 필터

N1과 N4는 같은 두 컬럼을 반대 순서로 가진 불완전 중복 후보입니다. 계좌번호 동등 조건과 거래일자 범위를 함께 쓰는 조회에서는 N1이 먼저 계좌를 좁힐 수 있어 N4보다 유리합니다. 거래일자만 범위 조건인 조회는 거래일자로 시작하는 PK가 이미 접근 경로를 제공할 수 있습니다.

따라서 해당 조회 조합만 고려하면 N4 제거를 검토할 수 있습니다. 다만 N4는 거래일자와 계좌번호만 필요한 쿼리를 커버할 수도 있고, 종목코드 조건의 N3와도 역할이 다릅니다. N4의 실제 효용은 SELECT 컬럼, 데이터 분포, 실행계획과 읽기량을 확인한 뒤 결정해야 합니다. 사진에 언급된 표 3-4의 분포 수치가 없으므로 여기서는 구조상 후보만 식별합니다.

완전히 같은 인덱스인지, 선두 키를 공유하는지, 특정 조건 조합에서 한 인덱스가 다른 인덱스보다 효율적인지는 구분해서 판단합니다. PK 인덱스는 기본키 제약을 유지하는 역할도 고려해야 합니다.

설계 점검 순서

  1. 실제 SQL의 필수·선택 조건, 조인, 정렬, 반환 컬럼을 모읍니다.
  2. 조회 빈도와 각 조건의 실제 일치 행 수를 확인합니다.
  3. 복합 인덱스의 선두 조건, 범위 시작·끝, 필터 조건을 구분합니다.
  4. 테이블 ROWID 방문과 정렬·TEMP 비용을 비교합니다.
  5. 읽기 성능 이득과 저장 공간, DML 유지 비용을 함께 평가하고 실행계획으로 검증합니다.
