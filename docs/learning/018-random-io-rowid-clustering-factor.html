2장. 랜덤 I/O와 테이블 접근

인덱스에서 찾은 ROWID로 테이블 블록을 읽는 과정과 버퍼 캐시, 클러스터링 팩터의 관계를 정리합니다. Oracle의 일반적인 힙 테이블과 B-tree 인덱스를 기준으로 설명합니다.

SQL 튜닝은 랜덤 I/O와의 전쟁이다

인덱스를 사용해도 필요한 행이 여러 테이블 블록에 흩어져 있으면 블록을 개별적으로 찾아가는 비용이 커집니다. 인덱스에서 충분히 조건을 걸러 테이블 방문을 줄이거나, 필요한 컬럼을 인덱스에 포함해 테이블 방문을 생략할 수 있습니다. 많은 행을 읽는 경우에는 전체 스캔이 더 유리할 수도 있습니다.

이 표현은 인덱스를 사용했다는 사실보다 그 뒤의 테이블 접근량이 중요하다는 뜻입니다. SQL 튜닝에는 불필요한 논리적 읽기, 정렬, 조인 연산을 줄이는 일도 포함됩니다.

파티션 프루닝과 인덱스 스킵 스캔

구분파티션 프루닝인덱스 스킵 스캔
줄이는 대상읽을 필요가 없는 파티션복합 인덱스 내부의 불필요한 구간
예시주문일로 월별 분할한 테이블에서 2월 조건으로 다른 월 제외(성별, 연봉) 인덱스에서 성별 조건 없이 연봉 조건으로 탐색
관점어느 파티션을 읽을 것인가인덱스 안에서 어떻게 찾을 것인가

프루닝 후 남은 파티션에서도 인덱스 탐색이나 전체 스캔을 할 수 있습니다. 프루닝과 스킵 스캔은 함께 적용될 수도 있으며, 어느 쪽도 테이블 랜덤 접근을 반드시 없애는 것은 아닙니다.

TABLE ACCESS BY INDEX ROWID

인덱스 리프의 각 엔트리에는 인덱스 키 값과 ROWID가 들어 있습니다. 키로 조건에 맞는 엔트리를 찾고, 필요한 컬럼이 인덱스에 없으면 ROWID로 테이블의 행을 찾아갑니다.

인덱스 키 탐색 → ROWID 획득 → 테이블 블록 접근 → 블록 안의 행 조회

기본적인 이해는 찾은 행마다 ROWID로 테이블을 방문한다는 것입니다. 하지만 읽기 단위는 블록이므로 행 수와 물리적 읽기 횟수는 같지 않습니다. 100개 행이 같은 블록에 있으면 읽어 둔 블록을 재사용할 수 있고, 서로 다른 블록에 흩어져 있으면 더 많은 블록을 방문합니다. 실행 방식에 따라 ROWID를 모아서 블록 접근을 처리하기도 합니다.

ROWID, DBA, 메모리 주소의 차이

확장 ROWID에는 데이터 오브젝트 번호, 상대 데이터파일 번호, 블록 번호, 블록 내 행 번호가 포함됩니다. 파일 번호는 테이블스페이스 내 상대 번호입니다. DBA(Data Block Address)는 파일과 블록을 식별하는 주소이며, 디스크의 물리 섹터 주소라는 뜻은 아닙니다.

정보답하는 질문
DBA어느 데이터파일의 어느 블록인가?
ROWID어느 블록의 어느 행인가?
버퍼 메모리 주소그 블록의 복사본이 지금 메모리 어디에 있는가?
ROWID에서 대상 블록 식별
  → DBA 기반 해시 조회
  → 해시 체인의 버퍼 헤더 확인
  → 필요한 버퍼와 블록 버전 선택
  → ROWID의 행 번호로 행 조회

캐시에 없으면 블록을 읽어 버퍼에 적재합니다. 캐시에서 밀려난 뒤 다시 적재되면 메모리 위치는 달라질 수 있지만, 캐시 퇴출 자체가 데이터파일 내 블록 위치나 ROWID를 바꾸지는 않습니다.

개념적으로 DBA를 키로 현재 캐시 위치를 찾는 맵입니다. 다만 같은 블록의 일관성 읽기용 복사본 등이 여러 개 있을 수 있으므로 실제 구조는 단순한 일대일 맵이 아닙니다.

BCHR: 버퍼 캐시 적중률

BCHR(Buffer Cache Hit Ratio)은 필요한 블록을 새로 읽지 않고 버퍼 캐시에서 찾은 비율입니다. 개념식은 다음과 같으며, 실제 통계 계산에서는 캐시를 우회하는 직접 읽기 등을 구분해야 합니다.

BCHR = (1 − 캐시로 읽어 들인 물리적 읽기 / 논리적 읽기) × 100%

논리적 읽기 1,000회 중 물리적 읽기가 100회라면 적중률은 90%입니다. 적중률이 높아도 불필요한 논리적 읽기가 많으면 비효율적인 SQL일 수 있습니다. 적중률과 함께 전체 읽기량을 확인해야 합니다.

클러스터링 팩터와 블록 재사용

클러스터링 팩터는 인덱스 키 순서로 행을 찾아갈 때 테이블 블록이 얼마나 자주 바뀌는지를 나타내는 통계입니다. 보통 테이블 블록 수에 가까우면 좋은 편이고, 행 수에 가까우면 행들이 인덱스 순서와 무관하게 흩어진 편입니다.

인덱스 순서대로 방문하는 테이블 블록
모여 있는 경우: A → A → A → B → B → B
흩어진 경우:   A → D → B → A → C → D

좋은 경우에는 같은 블록에서 여러 행을 연이어 가져오기 쉽습니다. 흩어진 경우에도 블록이 캐시에 남아 있으면 물리적 읽기를 피할 수 있지만, 여러 블록을 찾아가야 합니다. 클러스터링 팩터는 실제 디스크 읽기 횟수 자체가 아닙니다.

버퍼 캐시는 블록을 보관해 재사용을 가능하게 합니다. 좋은 클러스터링은 그 재사용이 연이어 일어나기 쉽게 합니다. 클러스터링 팩터가 좋기 때문에 캐시가 블록을 보관하는 것은 아닙니다.

이 배치는 순전히 우연만으로 결정되지 않습니다. 예를 들어 시간순으로 들어오는 주문은 주문일이 비슷한 행끼리 모일 수 있어 주문일 인덱스에 유리합니다. 같은 테이블도 고객번호 인덱스로 읽으면 여러 블록을 오갈 수 있습니다.

특정 인덱스 키에 맞춰 테이블을 재배치해 개선할 수도 있습니다. 그러나 이후 변경으로 흐트러질 수 있고, 다른 인덱스에는 불리할 수 있습니다. 인덱스만 재생성하면 테이블 행 배치는 그대로이므로 근본적인 개선이 되지 않습니다.
