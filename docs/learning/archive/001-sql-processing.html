SQL 처리, 캐시와 실행 계획

SQL 처리 흐름과 Oracle의 캐시 동작, MySQL의 옵티마이저 진단을 구분해 정리합니다.

SQL 실행 흐름

일반적인 흐름은 SQL 문장 → 파싱 → 의미 분석·바인딩 → 논리 실행 계획 → 옵티마이저 → 물리 실행 계획 → 실행기입니다. 옵티마이저가 실행 방법을 고르면 실행기가 계획을 수행합니다.

프로시저는 옵티마이저 다음 단계가 아니라 SQL과 제어 흐름을 묶는 루틴입니다. 호출되면 내부 SQL이 데이터베이스에 따라 준비 시점이나 실행 시점에 파싱·최적화될 수 있습니다.

Oracle 라이브러리 캐시와 파싱

Oracle은 SQL 텍스트의 해시값으로 라이브러리 캐시의 후보 커서를 찾고 텍스트를 비교합니다. 텍스트 일치만으로 공유가 확정되지는 않으며, 기존 커서와 실행 환경 등이 호환되어 재사용할 수 있어야 합니다.

  • 재사용 가능한 커서 발견: 소프트 파싱으로 기존 커서와 실행 계획을 재사용합니다. 보통 옵티마이저 최적화와 실행 계획 생성은 다시 하지 않습니다.
  • 재사용할 커서 없음: 하드 파싱을 수행해 새 커서를 만들고 최적화 및 실행 계획 생성을 진행합니다.
소프트 파싱도 파싱 요청입니다. 구문·권한 확인 같은 작업이 남을 수 있어 “파서를 완전히 건너뛴다”라고 표현하는 것은 지나친 단순화입니다.

라이브러리 캐시와 DB 버퍼 캐시

라이브러리 캐시는 실행 가능한 SQL·PL/SQL과 재사용 가능한 커서를 보관하고, DB 버퍼 캐시는 데이터 파일에서 읽어 온 Oracle 데이터 블록의 사본을 보관합니다. 전자는 SQL 실행 코드의 재사용, 후자는 데이터 블록 접근을 위한 캐시입니다.

DB 버퍼 캐시도 CPU의 L1·L2·L3 캐시 같은 하드웨어 캐시가 아니라, SGA 안에 Oracle이 관리하는 메모리 영역입니다. 블록이 버퍼 캐시에 있으면 메모리에서 읽어 데이터 파일 물리 읽기를 피할 수 있습니다. 없으면 데이터 파일에서 블록을 읽어 캐시에 올린 뒤 사용합니다.

버퍼 캐시에서 블록을 찾을 때 Oracle은 블록 주소를 해시해 해당 버퍼 체인으로 이동한 뒤 체인을 탐색합니다. cache buffers chains 래치는 체인을 검색·추가·제거할 때 공유 메모리 구조를 보호합니다. 버퍼 캐시는 같은 인스턴스의 여러 프로세스가 공유합니다.

래치는 SGA 내부 구조를 짧은 시간 보호하는 저수준 직렬화 장치입니다. 트랜잭션이나 행을 보호하는 enqueue 락과는 다른 메커니즘입니다. 특정 블록이나 체인에 접근이 몰리면 래치 경합으로 대기와 동시성 저하가 생길 수 있습니다. 불필요한 버퍼 겟을 줄이는 SQL 튜닝이 도움이 되지만, 핫 블록의 원인에 따라 데이터 구조나 애플리케이션의 접근 패턴도 살펴야 합니다.

두 캐시는 모두 소프트웨어가 관리하는 메모리 캐시지만, 라이브러리 캐시는 실행 코드에, 버퍼 캐시는 데이터 블록에 작동합니다.

동적 SQL과 하드 파싱

프로그램이 값까지 SQL 문자열에 이어 붙이면 실행마다 SQL 텍스트가 달라질 수 있습니다. 예를 들어 WHERE id = 10과 WHERE id = 11은 텍스트가 다릅니다. Oracle의 기본 CURSOR_SHARING=EXACT에서는 이런 문장들을 같은 커서로 공유하지 않으므로, 각 문장에 대해 하드 파싱이 늘어날 수 있습니다.

PreparedStatement로 SQL 모양을 고정하고 값을 바인드하면 여러 값으로 실행해도 같은 SQL 텍스트를 재사용할 가능성이 커집니다. 매 실행마다 prepare 호출이 있더라도 서버가 기존 공유 커서를 재사용할 수 있습니다.

하드 파싱이 많으면 CPU 사용과 라이브러리 캐시·딕셔너리 접근 및 동기화 부담이 커져 I/O보다 파싱 경로가 병목이 되는 경우가 있습니다. 다만 실제 병목이 되는지는 쿼리 실행량과 비용, 캐시 상태 등 부하에 따라 달라집니다. 여기서 말하는 라이브러리 캐시 미스는 데이터 블록 캐시 미스와 다른 종류입니다.

옵티마이저와 실행 계획

옵티마이저는 후보 실행 계획의 예상 비용을 바탕으로 실행 계획을 선택합니다. 가능한 모든 경로를 빠짐없이 비교한다고 단정할 수는 없습니다. 선택한 계획을 실제로 수행하고 결과 행을 돌려주는 것은 실행기입니다.

optimizer_trace는 MySQL의 진단 기능입니다. 최적화 과정, 비용 평가, 경로 선택 이유 등을 확인할 수 있지만 모든 가능한 계획을 완전하게 나열한다고 보장하지 않습니다. 선택된 계획은 EXPLAIN으로 확인하며, 실행 후 실제 정보를 보려면 지원되는 버전에서 EXPLAIN ANALYZE를 사용합니다.

힌트는 인덱스나 조인 순서처럼 특정 옵티마이저 선택을 유도하거나 제한합니다. 적용할 수 없거나 다른 제약과 충돌하면 무시될 수 있으므로, 특정 전체 실행 계획을 언제나 강제한다고 보면 안 됩니다.

optimizer_trace는 MySQL 용어입니다. 다른 DBMS의 옵티마이저 진단 방법과 힌트 규칙은 제품마다 다릅니다.

데이터 딕셔너리와 라이브러리 캐시

데이터 딕셔너리는 데이터베이스 구조, 사용자, 권한, 스키마 객체와 같은 메타데이터를 관리합니다. 저장 프로시저·함수·트리거도 데이터베이스 객체로 등록됩니다.

Oracle에서는 컴파일된 PL/SQL 프로그램 단위가 데이터베이스에 저장되고, 호출될 때 공유 풀의 라이브러리 캐시에 적재되어 실행됩니다. 라이브러리 캐시에는 SQL 커서와 실행 계획, PL/SQL 실행 형태, 객체 핸들과 제어 구조가 포함됩니다.

객체 간 의존관계는 딕셔너리에서도 관리되며, 객체가 변경되면 의존하는 캐시 객체를 무효화하는 데 쓰입니다. 라이브러리 캐시의 락과 핀은 객체를 찾고 사용하거나 변경할 때 동시성을 조정합니다.

기억할 점

재사용 가능한 커서가 있으면 기존 실행 계획을 쓰고, 없거나 공유할 수 없으면 하드 파싱으로 새 실행 계획을 만든다.

그러므로 캐시 조회는 SQL 텍스트로 시작하지만, 실제 재사용 여부는 텍스트 외의 공유 조건에도 달려 있습니다.
