Oracle 저장 구조와 데이터 파일

세그먼트·익스텐트·데이터 블록은 Oracle의 논리적 공간 단위이며, 데이터 파일은 이를 디스크에 담는 물리적 파일입니다.

논리 구조인가, 물리 구조인가?

세그먼트 → 익스텐트 → Oracle 데이터 블록은 모두 논리적 저장 구조입니다. Oracle이 공간을 나누고 객체에 할당하는 단위이며 운영체제가 이 이름과 경계를 직접 인식하지는 않습니다.

데이터 파일(data file)은 테이블스페이스의 내용을 실제로 저장하는 물리적 파일입니다. 파일 시스템이나 ASM 같은 저장 계층을 통해 디스크에 존재하고, 운영체제 블록에 저장됩니다.

블록은 논리 단위지만 실제 디스크의 일정 바이트에 대응합니다. 따라서 “물리 저장과 연결되어 있다”는 말은 맞지만, Oracle 블록을 곧바로 디스크 섹터나 OS 블록과 같은 것으로 보면 안 됩니다.

세그먼트, 익스텐트, 블록의 관계

  • 세그먼트: 테이블 데이터나 인덱스처럼 하나의 논리 저장 구조에 할당된 익스텐트들의 집합입니다.
  • 익스텐트: 한 번에 할당되는, 논리적으로 연속된 여러 데이터 블록입니다.
  • 데이터 블록: Oracle이 데이터를 읽고 쓰는 최소 논리 단위입니다. Oracle 문서에서는 이를 Oracle block 또는 page라고도 부릅니다.

테이블·인덱스 같은 스키마 객체는 스키마 안에서 이름과 의미를 갖는 논리 구조이고, 세그먼트는 그 객체의 저장 구조에 공간을 할당하고 추적하는 단위입니다. 모든 객체가 실제 데이터를 저장하는 것은 아닙니다. 테이블은 행을 저장하고 인덱스는 인덱스 항목을 저장하지만, 뷰는 질의 정의를 가진 메타데이터이므로 자체 데이터 세그먼트가 없습니다. 객체를 “논리적 정의이면서 실제 데이터를 가진 것”이라고 일반화하기보다는, 저장 객체의 정의와 실제 저장 공간을 구분하면 정확합니다.

단순한 비분할 테이블은 보통 테이블 데이터 세그먼트 하나에 대응하므로 객체가 익스텐트를 직접 묶는다고 생각해도 큰 문제는 없지만, Oracle에서는 세그먼트를 거쳐 익스텐트들을 묶어 관리합니다. 분할 테이블은 파티션별 세그먼트를 가질 수 있고, 인덱스나 LOB 데이터도 별도 세그먼트를 가질 수 있어 객체와 세그먼트가 항상 일대일인 것은 아닙니다. 또한 지연 세그먼트 생성이 적용되면 테이블 정의가 있어도 첫 행을 넣기 전까지 저장 세그먼트가 만들어지지 않을 수 있습니다.

세그먼트가 익스텐트를 묶는 이유는 객체별 저장 공간의 경계와 상태를 관리하기 위해서입니다. 예를 들어 테이블에 공간이 더 필요하면 해당 세그먼트에 익스텐트를 추가해 확장하고, Oracle은 세그먼트의 블록 사용 상태와 high water mark 등을 추적합니다. 이렇게 블록을 하나씩 객체에 할당하는 대신 익스텐트 단위로 공간을 늘리면 공간 할당을 관리하기 쉽습니다. 세그먼트는 물리적으로 붙어 있는 영역이라기보다, 객체에 속한 익스텐트들을 묶는 논리적 저장 단위입니다.

테이블에 공간이 더 필요하면 Oracle은 블록 하나씩이 아니라 익스텐트를 추가로 할당해 세그먼트를 확장합니다. “논리적으로 연속”은 Oracle 주소 공간에서 연속이라는 뜻이며, RAID나 파일 시스템 때문에 실제 디스크 위치까지 연속이라고 보장하지는 않습니다.

익스텐트는 데이터 파일 하나의 블록 범위에 저장되고, 세그먼트는 자신에게 할당된 익스텐트들로 구성됩니다. 세그먼트의 첫 데이터 블록에는 이 익스텐트들의 디렉터리가 있으므로 “세그먼트가 익스텐트 참조 집합을 가진다”는 비유는 가깝지만, 익스텐트는 단순한 임의 포인터가 아니라 세그먼트에 할당된 실제 논리 저장 공간입니다.

익스텐트의 블록은 한 세그먼트에 배타적으로 할당되므로, 일반적인 테이블 데이터 세그먼트와 인덱스 세그먼트가 같은 익스텐트를 나눠 쓰지는 않습니다. 각각 자신의 익스텐트들을 가집니다. 다만 테이블 클러스터처럼 한 세그먼트 안에 여러 테이블의 데이터를 저장하는 구조도 있어, “세그먼트 하나는 언제나 테이블 객체 하나”라고 일반화할 수는 없습니다.

테이블스페이스 → 세그먼트 → 익스텐트 → 데이터 블록은 Oracle 관점의 논리적 할당 관계이고, 파일 경로를 나타내는 물리 계층과는 별도로 생각하면 이해하기 쉽습니다. 여기서 화살표는 “안에 포함되거나 그 단위로 구성된다”는 뜻입니다. 각 단계가 다음 단계를 직접 관리한다는 뜻은 아닙니다.

익스텐트 하나의 블록들은 데이터 파일 안에서 논리적으로 연속하지만, 한 세그먼트의 여러 익스텐트가 파일 안에서 서로 이웃하거나 할당 순서대로 놓인다고 보장되지는 않습니다. 기본인 로컬 관리 테이블스페이스에서는 데이터 파일의 비트맵이 여유 공간을 추적하고, Oracle이 인접한 빈 블록을 찾아 익스텐트를 할당합니다. 따라서 세그먼트는 할당된 익스텐트들의 논리적 집합이고, 익스텐트 공간의 할당·해제는 테이블스페이스의 공간 관리 방식이 담당합니다.

데이터 파일은 어디에 연결되나?

테이블스페이스는 하나 이상의 데이터 파일을 사용합니다. 세그먼트는 한 테이블스페이스에 속하지만, 그 세그먼트의 익스텐트들은 같은 테이블스페이스 안의 여러 데이터 파일에 나뉘어 저장될 수 있습니다. 반면 익스텐트 하나는 데이터 파일 하나를 넘어서 걸치지 않습니다.

예를 들어 EMP 테이블의 세그먼트가 users01.dbf에 첫 익스텐트를, users02.dbf에 다음 익스텐트를 가질 수 있습니다. 각 익스텐트 안에는 여러 Oracle 블록이 있고, 데이터 파일 안의 특정 블록 오프셋이 그 블록을 담습니다.

관계를 줄여 그리면 다음과 같습니다.

논리: 테이블스페이스 → 세그먼트 → 익스텐트 → Oracle 블록
물리: 테이블스페이스의 데이터 파일 → OS 저장 블록
연결: 논리 블록은 데이터 파일의 공간에 기록되고, Oracle은 이 매핑으로 블록을 읽고 씁니다.

Oracle에서 DBA는 Data Block Address로, 데이터 파일 번호와 블록 번호로 Oracle 데이터 블록의 위치를 식별합니다. 이는 데이터 파일 안에서의 블록 주소이지, 디스크 장치 자체를 가리키는 주소는 아닙니다. 행을 식별하는 ROWID는 파일·블록 정보에 행 위치를 더한 별도의 주소입니다.

기억할 점

세그먼트·익스텐트·Oracle 블록은 논리적 할당 단위이고, 데이터 파일은 그 논리 공간을 디스크에 저장하는 물리 파일이다.

세그먼트는 한 테이블스페이스에 속하면서 그 안의 여러 데이터 파일에 걸쳐 저장될 수 있지만, 익스텐트 하나는 항상 한 파일 안에 있습니다.
