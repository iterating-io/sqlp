I/O 튜닝과 SQL의 읽기량

SQL이 요구하는 I/O를 줄이는 방법과 저장장치가 I/O를 처리하는 성능을 함께 살핍니다.

I/O 튜닝의 목적

SQL 튜닝 관점에서는 불필요한 데이터 읽기를 줄여 데이터베이스가 처리해야 할 I/O 수요를 낮추는 것이 중요한 목표입니다. 필요한 행과 열만 읽고, 적절한 접근 경로를 선택해 읽는 블록과 데이터 양을 줄입니다.

다만 I/O 튜닝 전체가 SQL의 읽기량 감소만을 뜻하지는 않습니다. 시스템이 I/O 병목 상태라면 저장장치의 처리량과 지연 시간, 파일 배치와 I/O 분산, 데이터베이스의 I/O 설정도 살펴 성능을 개선할 수 있습니다. 이는 물리 장치를 SQL이 직접 제어한다는 뜻이 아니라, 데이터베이스부터 저장장치까지의 처리 경로를 구성하고 튜닝한다는 뜻입니다.

먼저 실제 병목이 I/O인지 확인해야 합니다. CPU가 병목일 때 저장장치 튜닝만으로는 성능이 좋아지지 않을 수 있습니다.

요청 수와 크기를 무조건 줄이면 될까?

항상 그렇지는 않습니다. 예를 들어 전체 테이블 스캔은 여러 블록을 한 번에 읽는 큰 다중 블록 I/O를 사용해 효율을 높일 수 있습니다. 따라서 I/O 요청 수나 크기 하나만 최소화하기보다, 실제 작업의 응답 시간과 처리량을 기준으로 불필요한 읽기를 줄이고 남은 읽기를 효율적으로 처리해야 합니다.

캐시도 구분해야 합니다. 논리적 읽기(logical read)는 버퍼 캐시에서 블록을 확인하는 작업이고, 물리적 읽기(physical read)는 필요한 블록을 데이터 파일에서 읽어오는 I/O입니다. 논리적 읽기가 발생해도 블록이 캐시에 있으면 물리 디스크 읽기는 없을 수 있습니다. 따라서 논리적 읽기 수 감소가 물리적 I/O 감소와 항상 같은 것은 아닙니다.

Single-block I/O와 multiblock I/O

Single-block I/O 한 번에 Oracle 데이터 블록 하나를 읽습니다. 인덱스 탐색 후 ROWID로 테이블 블록을 찾는 경우처럼 인덱스 기반 접근에서 흔하지만, 인덱스 접근이 모두 single-block인 것은 아닙니다. 인덱스 fast full scan은 multiblock 읽기를 사용할 수 있습니다.

Multiblock I/O 한 번의 읽기로 여러 인접 블록을 가져옵니다. 전체 테이블 스캔이나 인덱스 fast full scan에서 흔히 쓰이며, DB_FILE_MULTIBLOCK_READ_COUNT와 플랫폼의 I/O 한도 등이 최대 크기를 제한합니다.

요청한 최대 크기만큼 항상 읽는 것은 아닙니다. Oracle 전체 스캔은 익스텐트 경계에서 요청이 줄어들 수 있고, 이미 캐시에 있는 블록이나 연속해서 읽을 수 있는 범위도 실제 요청 크기에 영향을 줍니다. 따라서 익스텐트 경계를 넘어 남은 용량을 채워 읽는다고 가정하지 않는 것이 좋습니다.

BCHR과 논리적·물리적 읽기

버퍼 캐시 히트율(BCHR)은 정해진 관찰 구간에서 요청한 블록을 버퍼 캐시에서 찾은 비율입니다. Oracle은 보통 1 - physical reads cache / (consistent gets from cache + db block gets from cache)로 계산하며, 누적값 전체보다 같은 부하 구간의 통계 차이를 비교하는 편이 유용합니다.

히트율과 접근 패턴이 비슷하게 유지된다면 논리적 블록 요청이 줄 때 물리적으로 읽는 블록 수도 대체로 줄어듭니다. 하지만 BCHR은 관측된 비율이지 물리적 I/O를 결정하는 고정 법칙은 아닙니다. 실행 계획, 캐시 상태, 직접 경로 읽기와 작업 종류에 따라 논리적 읽기와 물리적 읽기의 관계가 달라집니다. 따라서 SQL 튜닝은 BCHR만 올리는 것보다 불필요한 버퍼 겟과 물리적 읽기를 함께 살피는 것이 중요합니다.

버퍼 캐시 미스가 나면 데이터 파일 블록을 캐시에 올리는 물리적 읽기 후 그 버퍼를 대상으로 논리적 읽기가 발생합니다. 이후 캐시 히트에서는 논리적 읽기만 발생합니다. Oracle의 “물리적 읽기”는 파일 시스템 캐시에서 처리될 수도 있으며, 일부 직접 경로 읽기는 버퍼 캐시를 우회합니다.

SQL 실행 중 논리적 I/O는 무엇을 읽나?

Oracle에서 논리적 I/O, 즉 버퍼 I/O는 서버 프로세스가 DB 버퍼 캐시의 블록 버퍼를 읽거나 쓰는 작업입니다. 통계에서는 보통 버퍼 겟(buffer gets), 일관 읽기 겟(consistent gets), 현재 모드 블록 겟(db block gets) 등으로 나타납니다. 실행 중에는 테이블이나 인덱스의 데이터 블록을 읽는 일이 대표적입니다.

요청한 블록이 버퍼 캐시에 있으면 논리적 읽기만 일어납니다. 캐시에 없으면 데이터 파일에서 블록을 읽어 캐시에 올리는 물리적 읽기가 먼저 발생하고, 이어 그 버퍼를 읽는 논리적 읽기가 발생할 수 있습니다. 그러므로 논리적 I/O는 디스크 장치에 직접 보내는 호출 횟수와 같은 뜻이 아닙니다.

SQL 파싱 단계에서는 라이브러리 캐시에서 재사용 가능한 SQL 커서를 찾고, 데이터 딕셔너리 캐시(행 캐시)에서 객체·권한 등의 메타데이터를 확인할 수 있습니다. 행 캐시에서 메타데이터를 찾는 작업 자체는 버퍼 캐시의 논리적 I/O와 다른 종류의 메모리 조회입니다. 다만 딕셔너리의 기본 테이블 블록을 가져와야 하면 그 블록을 읽는 버퍼 겟과 경우에 따라 물리적 읽기가 발생할 수 있습니다. 딕셔너리 정보는 데이터베이스에 영구 저장되며, 자주 필요한 정보는 SGA의 딕셔너리 캐시와 라이브러리 캐시에 유지됩니다.

DML은 데이터 블록을 버퍼 캐시에서 읽고 수정해 더티 버퍼로 만들며, DBWn이 나중에 데이터 파일로 기록합니다. 변경 복구에 필요한 리두는 리두 로그 버퍼를 거쳐 관리되고, 커밋 시 LGWR이 온라인 리두 로그에 기록합니다.

기억할 점

SQL I/O 튜닝은 불필요한 읽기 수요를 줄이는 데 집중하고, 전체 I/O 튜닝은 저장 경로의 처리 능력과 병목도 함께 다룹니다.
